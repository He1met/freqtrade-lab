## 四类原因分辨

1. **Step残差**：存在小于0.001的量化尾差，但不是阻塞主因。即便能执行向下量化请求，
   仍可能留下尾差；当前执行请求完全归零是min_notional条件。不能把全部超限归为浮点误差。
2. **最小名义**：直接阻塞点在portfolio_execution.executable_quantity。
   这是本合成协议固定规则，不是向真实Binance发单后的拒单事实。
3. **原生padding**：在这两次实际路径未触发，因为核心已返回“保持当前量”，adapter
   adjust_trade_position算出change=0，未发减仓单。锁定源码重算的partial回调min_stake为
   BTC58.33333333 / ETH23.33333333（5% reserve，stoploss=-0.1）；entry则75/30（-0.99封顶1.5）。
   更关键的是原生partial逻辑把该min检查用于**剩余仓位**，不能误称所有减仓订单本身须>=58.33。
4. **代码错误/缺口**：未发现此次算术或告警误报。缺口是“硬风险target不可按小额合法削减”
   时只有保留实际量+告警，没有已冻结的进一步降风险动作，导致硬上限实际不满足。
   是否真实交易所有reduce-only最小名义例外尚未验证，不能直接移除核心min_notional防线。

源码证据均为锁定52bc96f原生源码：
- exchange/exchange.py:1098–1128计算reserve及amount/cost取max；
- optimize/backtesting.py:719读取partial min；:759–783按step量化并检查remaining非0且<min_stake则拒绝；
- :855–933全额custom_exit默认amount=trade.amount；:944–950保留价格/数量精度处理。
- freqtradebot.py:2170 futures退出传reduceOnly=True；exchange.py:1424将其传给订单参数。
这证明原生代码支持减少/全平路径，不证明交易所现实中免除最小名义或一定成交。
